1-2. iOS 앱 아키텍처

선택: SwiftUI + MVVM + Repository 패턴 (TCA는 도입하지 않음).

기준MVVMTCA
학습 곡선낮음높음
테스트 용이성중간매우 높음
보일러플레이트적음많음
1인 개발 적합성★★★★★★★
화면 30개 이상 시 일관성중간매우 좋음

이유: 1인 개발에서 TCA는 가속이 아니라 감속입니다. 화면이 30개를 넘기 시작하고 상태가 얽히기 시작하면 그때 부분 도입(Feature 단위)이 더 현실적입니다. 처음부터 TCA를 깔면 단순한 즐겨찾기 토글 하나에도 Action/Reducer를 그려야 합니다.

Clean Architecture는 "축소판"으로만. 3-layer로 충분합니다:

  • Presentation: SwiftUI View + ViewModel(@Observable)
  • Domain: Drama, Episode, Schedule 모델 + …UseCase (옵션, 복잡한 흐름만)
  • Data: Repository 프로토콜 + SupabaseDramaRepository 구현체

레포지토리를 프로토콜로 끊어둬야 나중에 Supabase → 자체 백엔드(NestJS)로 갈아낄 때 ViewModel을 안 건드릴 수 있습니다.

Feature-first 폴더링을 강력 추천합니다. Layer-first(Views/, ViewModels/ 따로)는 화면이 늘어나면 한 기능 수정에 폴더 5개를 왔다갔다 해야 합니다.

추후 사용자가 늘어 빌드가 느려지면(>2분), 각 Feature/를 SPM 로컬 패키지로 분리합니다. 이때를 위해 Feature 간 직접 import를 금지하고 모두 Domain을 통해 통신하도록 처음부터 규칙을 잡으세요.

2. MVP 우선순위

"매일 들어오는 플랫폼"이 목표라면 재방문을 만드는 기능부터 깝니다. 커뮤니티는 사용자가 모이기 전에는 죽은 공간이고, 죽은 게시판은 신규 사용자를 쫓아냅니다.

우선순위기능이유출시 시점
P0편성표 조회(채널/날짜)앱 핵심 가치. 이게 없으면 앱이 아님v1.0
P0즐겨찾기 + 로컬 저장재방문 동기. 서버 없이도 동작 가능v1.0
P0방영 10분 전 푸시"왜 매일 켜는가"의 핵심v1.0
P0Apple 로그인 (게스트 포함)즐겨찾기 동기화 + 4.8 가이드 대응v1.0
P1검색(드라마명)편성표만으론 신규 드라마 찾기 불편v1.1
P1장르 필터v1.1
P1상세 화면(시놉시스/회차)TMDB 데이터로 빠르게v1.1
P2커뮤니티(게시판/댓글)사용자 1만 모인 후v2.0

P3배우 기반 검색, 출연작 알림TMDB person 데이터 필요v3.0
P4실시간 채팅운영 부담 큼. 정말 필요할 때v4.0+
핵심: P0 4개만 정확히 구현해도 "편성표 + 알림" 시장에서 충분히 경쟁력 있습니다. 한국에서 드라마 알림 시장은 비어 있습니다. 커뮤니티는 후행 기능입니다.

3. 화면 구성

탭바 5개 구조: [편성표] [즐겨찾기] [검색] [커뮤니티] [마이]

3-1. 편성표 탭 (Schedule)

┌──────────────────────────────────┐ │ ← 5월 24일(토) → [채널 ▼] │ ← 날짜 스와이프, 채널 필터 ├──────────────────────────────────┤ │ 19:30 KBS2 [LIVE] 드라마A 12회 │ ← 현재 방영중은 빨간 배지 │ ♡ 알림 ON │ ├──────────────────────────────────┤ │ 20:40 MBC 드라마B 8회 │ │ ♡ 알림 │ ├──────────────────────────────────┤ │ 21:50 SBS 드라마C (첫방) │ │ ♡ 알림 │ └──────────────────────────────────┘

상단: 가로 스크롤 가능한 날짜 캐러셀(±14일). 우측 상단: 채널 필터(다중 선택). 행 탭 → 드라마 상세.

3-2. 즐겨찾기 탭 (Favorites)

┌──────────────────────────────────┐ │ 내 드라마 (12) [편집] │ ├──────────────────────────────────┤ │ [🔴 NEW] 드라마A │ │ 오늘 19:30 12회 방영 │ ├──────────────────────────────────┤ │ 드라마B │ │ 내일 20:40 9회 (D-1) │ ├──────────────────────────────────┤ │ 드라마C (종영) │ │ 전체 16회 ▶ │ └──────────────────────────────────┘

상태 그룹: 오늘 방영 / 내일 / 이번주 / 종영. 종영작은 별도 섹션으로 내려서 활성 드라마에 집중시킵니다.

3-3. 검색 탭

상단: 검색바. 하단: 인기 검색어 + 장르 칩. 결과는 드라마/배우 탭 분리(배우는 v3).

3-4. 드라마 상세

┌──────────────────────────────────┐ │ [포스터 이미지] │ │ 드라마A · 2026 · KBS2 │ │ ♡ 즐겨찾기 🔔 알림 받기 │ ├──────────────────────────────────┤ │ [회차] [정보] [출연] [게시판] │ ← 세그먼트 ├──────────────────────────────────┤ │ 12회 5/24 19:30 │ │ 11회 5/23 19:30 ▶ │ │ ... │ └──────────────────────────────────┘

3-5. 커뮤니티 (드라마 게시판)

게시글 카드: 제목 / 작성자(닉네임) / 좋아요·댓글 수 / 스포일러 토글. 스포 게시글은 회색 마스킹 + "탭해서 보기".

3-6. 마이

프로필(닉네임, 가입일), 내 활동(쓴 글/댓글), 알림 설정, 차단 목록, 로그아웃, 회원 탈퇴(4.8 필수).

4. DB 테이블 설계

PostgreSQL 기준. 모든 PK는 uuid (Supabase 관행), 모든 테이블에 created_at, updated_at, 필요시 deleted_at(소프트 삭제).

4-1. ERD (텍스트)

users ──< favorites >── dramas ──< episodes │ │ │ ├──< drama_casts >── persons │ └──< drama_genres >── genres │ ├──< devices (푸시 토큰) ├──< posts >── comments ──< comment_likes │ │ │ └──< post_likes ├──< reports └──< blocks

중요 포인트
• like_count, comment_count는 비정규화 필드입니다. 좋아요할 때마다 count(*)를 돌리면 DB가 죽습니다. 트리거 또는 트랜잭션에서 증감.
• episodes.air_time은 반드시 timestamptz(UTC 저장). 클라이언트에서 KST 변환.
• dramas.title에 pg_trgm 인덱스로 한글 부분 검색 지원.
• 모든 PK는 uuid — 분산 환경에서 ID 충돌 방지, 추측 불가(보안).

4-3. RLS (Row-Level Security) 예시

Supabase는 RLS가 필수입니다. 안 켜면 익명 사용자가 다 읽고 씁니다.

alter table posts enable row level security;

create policy "posts_select_all" on posts
  for select using (is_hidden = false);

create policy "posts_insert_own" on posts
  for insert with check (auth.uid() = user_id);

create policy "posts_update_own" on posts
  for update using (auth.uid() = user_id);

create policy "posts_hide_blocked" on posts
  for select using (
    not exists (
      select 1 from blocks
      where blocker_id = auth.uid() and blocked_id = posts.user_id
    )
  );

5. API 설계

Supabase를 쓰면 대부분의 CRUD는 PostgREST가 자동 생성해주므로 직접 REST 설계는 복잡한 도메인 로직에만 적용합니다.

5-1. Supabase 자동 API (직접 사용)

# 오늘 편성표
GET /rest/v1/episodes?
    air_time=gte.2026-05-24T00:00:00%2B09:00&
    air_time=lt.2026-05-25T00:00:00%2B09:00&
    select=*,drama:dramas(id,title,poster_url,channel:channels(code,name))&
    order=air_time.asc

# 즐겨찾기 추가
POST /rest/v1/favorites
{ "user_id": "...", "drama_id": "..." }

5-2. Edge Function이 필요한 케이스 (직접 설계)

PostgREST로 어려운 것: 트랜잭션, 외부 API 호출, 무거운 집계, 푸시 발송.

POST /functions/v1/toggle-favorite
Authorization: Bearer <user_jwt>
{ "drama_id": "uuid" }

Response 200:
{
  "favorited": true,
  "push_jobs_scheduled": 12   // 즐겨찾기와 동시에 향후 12회차 알림 예약
}
GET /functions/v1/home-feed
Authorization: Bearer <user_jwt>

Response 200:
{
  "on_air_now": [...],         // 지금 방영중
  "starts_soon": [...],        // 1시간 이내 시작
  "favorites_today": [...],    // 즐겨찾기 중 오늘 방영
  "hot_posts": [...]
}
POST /functions/v1/posts/{post_id}/report
{
  "reason": "SPOILER",
  "detail": "회차 정보에 결말 노출"
}

5-3. API 응답 컨벤션

// 성공

페이지네이션은 cursor 기반으로 처음부터. 인스타·트위터식 무한스크롤에서 offset은 LIMIT 20 OFFSET 10000 같은 쿼리에서 OOM을 만듭니다.

  3. RLS만 잘 짜면 백엔드 코드가 거의 0: 1인 개발자에게 결정적입니다.
  4. Edge Function(Deno/TypeScript)으로 복잡한 로직만 처리.

다음 단계 트리거: MAU 5만 이상 + Edge Function이 cold start로 느려지면 → 핫 패스만 NestJS + Fly.io로 빼냅니다. (Spring Boot는 1인 운영 부담이 큼)

7. 서버 아키텍처

7-1. 단계별 진화

[Phase 1: 0~5천 MAU] iOS App → Supabase (DB+Auth+EdgeFunc+Storage) ↑ └─ Crawler (Fly.io 1 VM, $2/월) [Phase 2: 5천~5만 MAU] iOS App → CloudFront/CloudFlare CDN → Supabase ↑ ↑ │ └─ Redis (Upstash) 캐시 레이어 └─ Crawler Worker (Cloud Run) [Phase 3: 5만+ MAU] iOS App → CDN → API Gateway ├─ Supabase (인증/RLS) ├─ NestJS API (홈피드/인기글 등 핫 패스) └─ Push Worker (별도 컨테이너, APNs HTTP/2 풀) Redis Cluster + 이벤트 큐(SQS)

7-2. 크롤러 분리가 필수인 이유

크롤러는 DB와 같은 머신에 두면 안 됩니다.

  • 차단당해서 IP 바뀌어야 할 때 DB까지 영향
  • 크롤러 죽으면 앱이 죽는 일 방지
  • 별도 cron 스케줄링 (매시간 / 매일 새벽 3시 전체 동기화)

Fly.io의 auto_stop_machines = true 옵션을 쓰면 크롤링 안 할 때는 머신이 꺼져서 월 $1~3 수준입니다.

8. 푸시 알림 구조

8-1. 가장 큰 문제: "1만 명에게 동시에 푸시 발송"

방영 시작 10분 전, 즐겨찾기 5천 명에게 동시 발송하면:

  • APNs는 HTTP/2로 stream 다중화. 한 connection으로 초당 ~1000건.
  • Edge Function의 timeout(30초)을 넘기기 쉬움.
  • 실패한 토큰 재시도 필요.

8-2. 권장 구조

[10분마다 cron] ↓ push_jobs 테이블에서 scheduled_at <= now() + 30s AND status = 'PENDING' 조회 ↓ 배치로 1000건씩 묶어 Push Worker로 전송 (이벤트 큐) ↓ Push Worker: APNs HTTP/2 connection pool, 동시 100 streams ↓ 성공: status = 'SENT' 실패 (410 Unregistered): devices.apns_token 무효화 실패 (다른): 재시도 큐 (max 3회)

8-3. 푸시 잡 미리 생성 (Pre-scheduling)

크롤러가 새 회차를 발견하면, 즉시 모든 즐겨찾기 사용자의 push_jobs를 미리 만들어둡니다:

-- 새 회차 등록 시 트리거
insert into push_jobs (user_id, episode_id, scheduled_at, payload)
select
  f.user_id,
  e.id,
  e.air_time - interval '10 minutes',
  jsonb_build_object(
    'aps', jsonb_build_object(
      'alert', jsonb_build_object(
        'title', d.title || ' ' || e.number || '회',
        'body', '10분 후 방영 시작!'
      ),
      'sound', 'default',
      'category', 'EPISODE_AIR'
    ),
    'drama_id', d.id,
    'episode_id', e.id
  )
from episodes e
join dramas d on d.id = e.drama_id
join favorites f on f.drama_id = d.id and f.notify_air = true
where e.id = NEW.id;

이렇게 하면 발송 시점에는 select … where scheduled_at <= now() 한 줄 쿼리로 끝납니다.

9-4. 신고 자동화

-- 같은 게시글에 신고 3회 누적 시 자동 hide
create or replace function auto_hide_on_report() returns trigger as $$
begin
  if (select count(*) from reports
      where target_type = NEW.target_type
        and target_id = NEW.target_id
        and status = 'PENDING') >= 3 then
    if NEW.target_type = 'POST' then
      update posts set is_hidden = true where id = NEW.target_id;
    end if;
  end if;
  return NEW;
end;
$$ language plpgsql;

자동 가림 후 운영자 검토 → 복원 또는 영구 삭제. Apple 가이드 1.2(UGC)는 24시간 내 처리를 요구합니다.

// crawler/src/kbs.ts
import { chromium } from 'playwright'

export async function crawlKBS(targetDate: Date) {
  const browser = await chromium.launch({ headless: true })
  const page = await browser.newPage({
    userAgent: 'Mozilla/5.0 (DramaApp Crawler; contact@dramaapp.com)',
    locale: 'ko-KR',
  })

  await page.goto(`https://program.kbs.co.kr/2tv/schedule/${formatDate(targetDate)}`)
  await page.waitForSelector('.schedule-item', { timeout: 10000 })

  const items = await page.$$eval('.schedule-item', (els) =>
    els.map(el => ({
      time: el.querySelector('.time')?.textContent?.trim(),
      title: el.querySelector('.title')?.textContent?.trim(),
      episode: el.querySelector('.episode')?.textContent?.trim(),
    }))
  )

  await browser.close()
  return items.map(normalizeKBS)
}

18. 확장 가능한 구조 설계 방법

지금 안 해도 되지만, 나중에 갈아엎지 않으려면 처음부터 지킬 5가지:

18-1. 인터페이스로 끊어둘 곳

// 처음부터 프로토콜로 정의
protocol DramaRepository {
  func schedule(date: Date, channelIds: [UUID]?) async throws -> [Episode]
  func toggleFavorite(dramaId: UUID) async throws -> Bool
}

// MVP 구현
final class SupabaseDramaRepository: DramaRepository { ... }

// 나중에 NestJS로 교체 시
final class NestJSDramaRepository: DramaRepository { ... }
// ViewModel은 한 줄도 안 바뀜

18-2. 도메인 이벤트 (나중에 큐로)

// 지금은 함수 직접 호출
async function onEpisodeCreated(episode) {
  await scheduleNotifications(episode)
  await invalidateCache(episode.dramaId)
}

// 사용자 많아지면 이벤트 버스(SQS/Pub-Sub)로 분리
await eventBus.publish('episode.created', { episodeId: episode.id })

이벤트 이름을 처음부터 명사+과거형(episode.created)으로 잡아두면 그대로 큐로 옮길 수 있습니다.

18-3. Feature Flag 처음부터

enum FeatureFlag {
  static var communityEnabled: Bool {
    RemoteConfig.shared.bool("community_enabled", default: false)
  }
}

서버 사이드(app_config 테이블)에 토글을 두고, 앱 업데이트 없이 기능을 끌 수 있어야 합니다. 커뮤니티가 터졌을 때 30초 안에 잠가야 합니다.

18-4. 멀티 채널 → 멀티 국가 확장

channels.type을 'BROADCAST'|'OTT'로 시작했지만, country_code 컬럼을 처음부터 추가하세요. 일본/대만 드라마 시장은 다음 단계 시장입니다.

18-5. 모듈화 타이밍

[Phase 1] 단일 앱 타겟 (현재) [Phase 2] WidgetKit Extension (오늘 편성 위젯) → Shared/ 모듈 분리 [Phase 3] watchOS 앱 → Domain 패키지 SPM 분리 [Phase 4] 빌드 시간 3분 초과 → Feature별 SPM 패키지

Domain 폴더의 모델/리포지토리 프로토콜은 Foundation 외 import를 금지하세요. 이게 미래의 모듈화를 가능하게 합니다.

19. 최종 요약 — "오늘 당장 할 일"

  1. DramaApp.xcodeproj를 SwiftUI로 재구성: 스토리보드 제거, @main DramaAppApp 생성, 탭 5개 골격
  2. Supabase 프로젝트 생성 (Seoul 리전), 위 DDL 그대로 적용
  3. TMDB API 키 발급 (무료)
  4. channels 테이블 시드: KBS2, MBC, SBS, tvN, JTBC 5개
  5. DramaRepository 프로토콜 먼저 정의, Mock 구현으로 UI부터

여기까지가 첫 주 작업입니다.

가장 강조하고 싶은 3가지

  1. 혼자 만들 수 있는 가장 큰 차별화는 "정확한 푸시 알림"입니다. 편성표만 있는 앱은 많지만 알림이 정확하지 않습니다. 여기에 1주를 더 써도 됩니다.
  2. 커뮤니티를 너무 빨리 열지 마세요. 사용자 1만 명 이하에서 게시판은 죽은 공간이고, 죽은 공간은 앱의 평판을 깎습니다.
  3. 크롤러 모니터링이 앱 코드보다 중요합니다. 새벽에 크롤러가 깨지면 사용자 1만 명이 동시에 잘못된 알림을 받습니다. Slack webhook 알림은 1일차에 박으세요.
